# 길픽 팀 헌법

## Core Principles

### I. 보호 브랜치 직접 푸시 금지

팀원과 자동화 도구는 `main`과 `develop` 브랜치에 직접 푸시해서는 안 된다(MUST NOT).
두 브랜치의 변경은 승인된 Pull Request를 통해서만 반영해야 한다(MUST).
호스팅 플랫폼이 지원하는 경우 저장소의 브랜치 보호 설정으로 이 규칙을 강제한다(SHOULD).

근거: 공유 브랜치의 검토 기록을 보존하고 미검토 변경의 유입을 막기 위함이다.

### II. 기능 브랜치와 Pull Request

모든 기능, 버그 수정, 리팩터링은 범위를 이름으로 식별할 수 있는 별도 브랜치에서
개발해야 한다(MUST). 작성자는 변경 내용과 검증 결과를 설명한 Pull Request를 열고,
병합 전에 다른 팀원 한 명 이상의 승인을 받아야 한다(MUST).

근거: 변경을 격리하면 검토, 추적, 되돌리기를 안정적으로 수행할 수 있다.

### III. AI 생성 코드의 사람 검토

변경 담당자는 AI가 생성하거나 수정한 모든 코드를 제출 전에 직접 검토해야 한다(MUST).
담당자는 정확성, 보안, 라이선스 우려, 프로젝트 적합성, 테스트 범위를 확인해야 하며,
컴파일 또는 AI 생성 테스트 통과만으로 코드를 승인해서는 안 된다(MUST NOT).
중요한 AI 보조 변경은 Pull Request에 밝혀야 한다(MUST).

근거: 코드를 만든 수단과 관계없이 최종 책임은 사람인 담당자에게 있다.

### IV. 환경 변수 기반 비밀 정보 관리

API 키, 비밀번호, 토큰, 자격 증명 등 비밀 정보는 환경 변수로 주입해야 한다(MUST).
승인된 비밀 정보 관리 도구를 사용하는 경우에도 애플리케이션에는 환경 변수로 전달한다.
비밀 정보를 소스, 설정 예시, 테스트, 로그, 문서에 커밋해서는 안 되며(MUST NOT),
예시 환경 파일에는 자리표시자 값만 포함해야 한다(MUST).

근거: 비밀 정보와 소스를 분리하면 우발적 노출을 줄이고 안전하게 교체할 수 있다.

### V. 공유 계약 변경의 팀 합의

API 명세, 외부에 공개된 요청·응답 계약, 데이터베이스 스키마 또는 마이그레이션 변경은
구현 전에 팀에 제안하고 명시적 합의를 받아야 한다(MUST). 합의 결과와 호환성 또는
마이그레이션 영향은 명세, 계획, 이슈, Pull Request 중 하나에 기록해야 한다(MUST).

근거: 공유 계약의 변경은 여러 담당 영역에 영향을 주며 큰 호환성 문제를 만들 수 있다.

### VI. 핵심 비즈니스 로직 테스트

핵심 비즈니스 규칙에는 정상 동작, 경계 조건, 주요 실패 사례를 다루는 자동화 테스트를
작성해야 한다(MUST). 핵심 로직 변경에는 관련 테스트 변경이 함께 포함되어야 하며,
병합 전에 해당 테스트가 통과해야 한다(MUST). 예외는 Pull Request에 사유를 기록하고
팀의 승인을 받아야 한다(MUST).

근거: 비즈니스 규칙은 제품의 핵심 동작이므로 반복 가능한 검증 수단이 필요하다.

### VII. 담당 범위와 파일 소유권 존중

팀원은 자신에게 할당된 범위에 필요한 파일만 수정해야 한다(MUST). 담당 범위 밖 파일을
변경하려면 해당 담당자 또는 팀과 사전에 조율하고, 변경 이유를 Pull Request에 기록해야
한다(MUST). 관련 없는 정리 작업은 별도 변경으로 분리해야 한다(MUST).

근거: 명확한 변경 경계는 병합 충돌, 예상하지 못한 회귀, 불분명한 소유권을 줄인다.

### VIII. 설명 가능한 코드 소유

모든 팀원은 자신이 제출하거나 담당하는 코드의 의도, 설계, 주요 제어 흐름, 선택의
장단점, 검증 방법을 설명할 수 있어야 한다(MUST). 담당자가 설명할 수 없는 코드는 충분히
이해하거나 수정하거나 담당자를 재지정하기 전까지 병합해서는 안 된다(MUST NOT).
소유권이나 이해 수준이 불명확하면 검토자는 코드 설명을 요청할 수 있다(MAY).

근거: 유지보수 가능성은 코드의 존재뿐 아니라 팀이 보유한 이해에 달려 있다.

## 필수 개발 제약

- 로컬 및 배포 설정은 비밀 정보를 환경 변수에서 읽고, 필수 값이 없으면 안전하게
  실패해야 한다(MUST).
- API 및 데이터베이스 변경 제안에는 팀 합의 전에 호환성, 배포, 롤백, 마이그레이션
  영향을 명시해야 한다(MUST).
- 핵심 비즈니스 로직은 집중된 자동화 테스트가 가능하도록 전송 계층이나 UI 관심사와
  충분히 분리해야 한다(MUST).
- Pull Request는 선언된 담당 범위로 제한해야 하며, 부수적 변경은 제거하거나 해당
  담당자의 명시적 승인을 받아야 한다(MUST).

## 개발 워크플로

1. 담당 범위와 영향받는 파일, API 또는 데이터베이스 계약 변경 여부를 정의한다.
2. 팀이 지정한 기준 브랜치에서 전용 기능 브랜치를 생성한다.
3. API 명세 또는 데이터베이스 구조 변경을 구현하기 전에 팀 합의를 받는다.
4. 비밀 정보를 소스 관리에서 제외하고 핵심 로직 테스트를 추가하며 최소 범위를 구현한다.
5. AI 보조 결과를 직접 검토하고 이해한 뒤 관련 자동·수동 검증을 실행한다.
6. 범위, 계약 변경 합의, AI 사용, 검증 결과를 설명하는 Pull Request를 연다.
7. 한 명 이상의 승인을 받고 검토 의견을 반영한 뒤 Pull Request를 통해서만 병합한다.

검토자는 보호 브랜치를 우회하거나, 필요한 합의나 테스트가 없거나, 비밀 정보를
노출하거나, 조율 없이 담당 범위를 벗어나거나, 담당자가 설명할 수 없는 변경의 병합을
거부해야 한다(MUST).

## Governance

이 헌법은 길픽 팀의 최우선 개발 정책이다. 다른 프로젝트 문서나 관행이 이 헌법과
충돌하면 이 헌법을 따른다.

개정안은 이유와 전환 영향을 설명하는 Pull Request로 제안하고, 병합 전에 팀의 명시적
합의를 받아야 한다(MUST). 개정으로 영향을 받는 템플릿과 지침은 같은 변경에서 함께
수정해야 한다(MUST).

헌법 버전은 시맨틱 버저닝을 따른다. 호환되지 않는 거버넌스 또는 원칙 변경은 MAJOR,
새 원칙이나 의무의 실질적 확대는 MINOR, 의무를 바꾸지 않는 명확화는 PATCH로 올린다.
Last Amended 날짜는 개정 채택일과 일치해야 한다(MUST).

모든 기능 계획은 구현 전과 설계 후에 Constitution Check를 통과해야 한다(MUST).
모든 Pull Request 작성자와 검토자는 병합 전에 해당 원칙 준수 여부를 확인해야 한다.
예외는 기한, 승인, 담당자, 해결 계획을 문서화해야 하며(MUST), 비밀 정보 커밋이나
보호 브랜치 직접 푸시는 예외로 허용할 수 없다(MUST NOT).
